Single source of truth. If code and this file disagree, flag it; do not silently pick one.

## Stack and environment
- Expo SDK 57, Expo Router, React Native, TypeScript/JS mix. iPhone: Expo Go from the App Store (SDK 57). Android: the preview build (EAS, APK), not Expo Go: expo-notifications cannot load in Expo Go on Android, and the app then runs with reminders marked unavailable (services/notificationsCore.ts)
- semver ^7.8.5 is a direct dependency only as a workaround for a Metro resolution failure on react-native-reanimated's nested semver (SDK 57); remove when the cause is understood.
- Local SQLite (expo-sqlite) is the source of truth; Firebase (Auth + Firestore) for backup/sync
- Dev on Windows/PowerShell/VS Code. Test devices: iPhone 13 Pro (iOS 26), Itel A60s (Android 12 Go, 32-bit)
- Folder structure: type-based (/components, /db, /sync, /services); screens live in /app per Expo Router

## Architecture
- Local-first: all reads/writes hit SQLite; sync is background and must fail silently (no error shown to user). Two exceptions, both muted lines in Settings only: the clock line (S-1, 2026-11-09, below) and the cursor line (R-1, 2026-11-13, below)
- Tables: habits, habitDays (normalised weekday rows, no JSON arrays), completions (composite primary key habitId + date). Completions use an explicit row per habit per day with completed true/false (not insert-on-complete)
- Sync tracking: a `synced` flag on each row, set false on local write, true after successful push; only unsynced rows are pushed
- Sync triggers: app foreground + every 5 minutes while open. No network-reconnect listener in v1 (avoids netinfo dependency)
- Conflict rule (revised after code audit; replaces the earlier sticky-true rule): last-write-wins on a per-row `updatedAt` (ms timestamp). Only user actions (add, edit, delete, toggle) set `updatedAt`, to `max(Date.now(), the row's updatedAt + 1)` since the 2026-11-09 decision S-1 (see "Decisions from the test-strategy audit"). System-generated rows (ensureTodayRows / backfill) get `updatedAt = 0` so they can never overwrite a real user action from another device or a previous install. Reason: sticky-true made unchecking impossible once a true had synced
- AI: server-side only via Cloud Function calling Gemini API (free tier Flash/Flash-Lite). Never call the AI API from the client
- Insight UI: expandable card on Home; insight text cached locally for offline viewing; offline with no insight shows a "check back once you're online" message
- Auth: Firebase Auth email/password; sessions persist locally so internet is needed only for first sign-up/sign-in

## Operations
- Habits: Add, Update (full edit via the add form, pre-filled), Delete = SOFT delete (`deleted` flag, synced like any field). All reads filter `deleted = false`. Changing frequency never alters past completion rows
- Completions: never user-added. On Home mount, lazily backfill every missing day per active habit as completed:false up to today, and ensure today's row exists. Only today's row is user-toggleable. No delete
- Onboarding: add once at signup, retakeable from Settings (retake ADDS suggested habits, never replaces). No delete
- Auth: signup; edit email/password in Settings (requires reauthenticateWithCredential first, handle auth/requires-recent-login). Account deletion OUT of scope

## Validation (summary; full tables in the published doc)
- habit.name: trim, then 1-30 chars. icon: string in fixed allowed list. frequency: {type:'daily'} or {type:'weekdays', days[]} with real array, valid weekday strings, no duplicates, at least 1. reminder_time: nullable; if set must match ^([01]\d|2[0-3]):[0-5]\d$
- completed: strict typeof boolean
- onboarding goal/lifestyle/biggest_challenge: fixed multiple-choice enums
- email: trim, lowercase, ^[^@\s]+@[^@\s]+\.[^@\s]+$, max 254; Firebase is authoritative (map auth/invalid-email, auth/email-already-in-use to friendly messages)
- password: raw (no trim), min 8; map auth/weak-password. confirm_password must match
- age: integer 18-99 (18 minimum avoids Kenya Data Protection Act 2019 s.33 parental-consent duty)
- UX: inline errors as the user types/leaves a field, Save disabled until valid, errors clear when fixed

## Scope (committed)
Full Figma prototype scope: Sign In/Up, 10-question onboarding, building-profile screen, 6-axis radar "Habit Profile", recommended routine, Home with XP progress ring, Habit Detail, Summary (day/week/month/year), Profile (level, streaks, lifetime stats and medals), Settings (your name, reminders and celebrations, habit packs, the plan retake and sign-out), Level-Up overlay, bottom tabs Home/Summary/Profile/Settings (corrected 2026-11-10: the app has had a separate Profile tab; this line said "Settings (profile merged in)" and three tabs). The Figma file has NO Add/Edit Habit screen; design it in the same visual language. XP is derived from completions and the reflections kept on the phone (no table, no stored total; docs/PACKS_REPORTS_SPEC.md sections 12 and 16). Splash: Expo native splash only
- Out of scope: social/multi-user, monetization, full encryption, account deletion

## Decisions made after the first code audit
- Naming: keep the existing camelCase in code and SQLite (habitId, habitName, reminderTime). The snake_case names in the validation doc are descriptive only
- Conflict rule: last-write-wins on updatedAt (see Architecture)
- Age gate: a required age field on the signup form, validated 18-99 BEFORE calling createUserWithEmailAndPassword, so no account is ever created for an under-18 user. Store age as a number. If onboarding includes an age-range question, it must not offer an under-18 option
- firstName/lastName (revised 2026-11-04, replaces "remove from signup and from the users document"): asked at sign-up (required; trimmed, 1-40 characters, letters in any script, spaces, hyphens and apostrophes) and editable in Settings > Your name. Stored on the user's own Firestore users document (firstName, lastName; optional in the rules so older builds still sign up), as Auth displayName "First Last", and as a copy on the device (AsyncStorage profile:name:v1, read with the sign-in marker) so Home's greeting has it on the first render offline. Reason: used only for the greeting; never sent to Gemini or any analytics, and never shown in the admin screens. The privacy policy and the Play Data safety form must list "Name"
- Dates: one shared helper that returns the LOCAL date as YYYY-MM-DD (never toISOString().split('T')[0], which is UTC and wrong from 00:00-03:00 in Kenya). Use it everywhere a date is created or compared

## Decisions made after the second audit
- habitNotes: REMOVED (not in the locked design). Can be re-added later by a migration
- habits primary key: TEXT id generated on the device as a UUID (ask before adding expo-crypto; do not install anything without approval). Reason: INTEGER ids restart on reinstall and collide across devices, and they feed Firestore document ids
- habits columns: habitId, userId, habitName, icon, frequencyType ('daily' | 'weekdays'), reminderTime (nullable), source ('user' | 'ai_suggested'), createdAt, updatedAt, deleted, synced
- habitDays(habitId, day): composite primary key, day in mon/tue/wed/thu/fri/sat/sun. Rows exist only for habits with frequencyType = 'weekdays'. Chosen over a JSON column so the schema is in 3NF for logbook Meeting 3
- completions: primary key (habitId, date); columns habitId, date, completed (0/1), updatedAt, synced. No completionId
- Weekday habits on unscheduled days: no completion row is created and the habit is not shown on Home. Backfill only creates rows for scheduled days
- Icons are stable string ids, not emoji. PLACEHOLDER list (to be confirmed): book, water, run, meditate, sleep, food, study, work, music, money, heart, star
- Per-user data: every habit row carries userId (the Firebase uid) and every read filters by the signed-in user
- Local database: a one-time dev wipe is acceptable (test data only). From now on schema changes use versioned migrations via PRAGMA user_version, verified against the Expo SDK 57 expo-sqlite docs
- Schema setup must be awaited before the first query (the local database is now opened and migrated before first render, through getDatabase() in app/_layout.tsx)
- Meeting 2 demo scope: habits add / edit / soft-delete with validation, completion toggle, signup with validation and the age gate. Deferred until after Meeting 2: backfill, onboarding, email/password editing, habit sync
- The habit sync columns (updatedAt, synced, deleted) exist from day one, but the sync work itself is build step 2. That step must also: sync at app launch and right after login, pull data down from Firestore on login (the report promises cross-device preservation), fix the race where a tap during a push is overwritten, and use the same ids as the local keys. Known failures from the old engine (iPhone log, SDK 57): Firestore permission denied on a completions push, and SQLite NOT NULL constraint failed on completions.completed during the merge write. Diagnose first in the sync step.
- If time runs short, cut in this order: Level-Up overlay, Habit Detail, radar chart, Summary charts (keep basic stats), reminders, then trim onboarding from 10 questions. Never cut: auth, habit CRUD, completions, Home, Settings, local-first sync, a minimal onboarding with AI recommendation, the AI insight card, simple XP. This is a risk plan only; the committed scope above has not changed
- iPhone 13 Pro: the App Store Expo Go is SDK 57, as reported by the Expo CLI when the phone opened the project, and the CLI says iOS Expo Go cannot be downgraded. Android: the SDK 55 changelog says Expo Go on Android is installed via the Expo CLI; whether it runs on the Itel A60s (32-bit, Android 12 Go) is not yet confirmed.

## Decisions from the test-strategy audit (2026-11-09)
Decided after the spec red-team in docs/TEST_STRATEGY.md (Part B). Each rule has an "Odd states" line. Pack, reflection, Vitality and area rules are in docs/PACKS_REPORTS_SPEC.md section 17. Fixes land in Phase 1b.
- S-1, monotonic updatedAt (built in Phase 1b): every user write (add, edit, delete, toggle) stamps `updatedAt = max(Date.now(), the row's updatedAt + 1)`, so an edit is never older than the copy it replaces. Reason: with `Date.now()` alone, a phone whose clock is behind (or was moved back) loses its edits: either its own next pull keeps the server copy, or the rules refuse the push ("updatedAt went back").
  - Where: db/stamp.js. The previous value is read by the same SQL statement that writes the new one (`MAX(?, updatedAt + 1)` in updateHabit and softDeleteHabit, `MAX(excluded.updatedAt, completions.updatedAt + 1)` in toggleCompletion's upsert): no extra query, no race. addHabit stamps now (a new row has no previous value). System rows (ensureTodayRows) stay 0; pulled rows keep the remote value; db/devSeed.js (dev only) is unchanged.
  - Stuck rows: rows stamped more than a day ahead (the phone's clock was ahead, so the rules refused them) are re-stamped to now at the start of a push, in one queued transaction (db/syncCore.js restampFutureRows): only this uid's UNSYNCED rows; synced rows and other users' rows are never touched; system rows can't match. Guarded: it runs only when a dirty row has `updatedAt > now + 1 day`, because the statement scans completions (about 13 ms for 100,000 rows on a PC, several times that on the Itel).
  - Clock suspect: a push refusal of a row stamped within the last 24 hours by the phone's clock, in a cycle whose pull reached the end (so no newer server copy is known), marks the cycle "clock suspect". The engine counts such cycles (status `clockSuspectCycles`, memory only): +1 for a cycle that marks it, +1 for each later cycle that reaches the push with no accepted write; unchanged by a cycle that stops before the push or fails (offline); 0 after any accepted write, on sign-out (stop), sign-in (start) and app restart.
  - The clock message (one of the two exceptions to "fail silently"; the other is R-1's cursor line): when `clockSuspectCycles` is 2 or more, Settings shows, muted, directly under its title, the line "Backup paused: your phone's date and time look wrong. Set them to automatic and your changes will back up." One message, wrapping allowed. Never on Home, never a dialog, never on the startup path (a test checks which files read it). It goes after the next accepted push.
  - Known limitation (accepted 2026-11-09): Home's on-time/late status and the completion-time samples read a completion's `updatedAt` as its tick time. After the clock moved back, a tick is stamped previous + 1 ms, and a re-stamped row carries the time of the re-stamp, so those rows can show "late" or drop out of the samples. Only rows whose phone clock was wrong are affected (docs/BUG_LOG.md).
  - Rollback: no schema change. An older bundle stamps `Date.now()` again (the old behaviour), has no re-stamp step (stuck rows stay stuck, as before) and ignores the status field, which is never stored. Stamps written by the new code are valid for it and for the rules; no Firestore rules change.
  - Odd states: a clock behind or moved back (fixed by the rule); a clock more than a day ahead (pushes refused; the Settings line after two cycles; fixed by re-stamping once the clock is right); offline cycles (don't count); two phones editing the same row before either has pulled the other's edit: the higher stamp wins even if it was not the later edit in real time. That last case is a documented last-write-wins limit, not a bug. Tests: tests/clock-skew.test.ts, tests/sync-status-line.test.ts, tests/stamp.test.ts.
- S-2, clock-ahead creation: a habit's `createdDate` is clamped to `min(createdDate, today)` wherever it is computed with `today` (XP, perfect days, streaks, Vitality, the radar, Summary), and only that: no past day is invented for it.
  - Odd states: a habit created while the phone's clock was ahead, then the clock fixed: it counts from today instead of from its future date. Built in Phase 1b (2026-11-10): `clampCreatedDates` in utils/gamification.ts, applied on entry by computeStreaks, countPerfectDays (so XP), dailyCompletion (so Vitality and the radar) and computeSummary. Tests: tests/decided-rules.test.ts (S-2), including a scan that fails if any other app file starts reading createdDate.
- S-6, device settings: the notification settings (`prefs:notifications:v1`) and the celebrations switch (`prefs:celebrations`) are settings of the phone, shared by every account signed in on it, not per account.
  - Odd states: a second account signing in on the same phone keeps the first account's switches. Scheduled reminders themselves are per account: sign-out cancels them. Test: tests/decided-rules.test.ts (S-6, pinned).
- P-8, older code never drops newer fields (built in Phase 1b, 2026-11-13): every stored record's parser accepts and ignores unknown fields, and a save keeps them, so an OTA rollback or a launch from the embedded bundle can't lose data a newer update added. Covered: the packs record and the mirror's copy of it, the area map, the reflections record and the notification settings; the celebrated keys and the celebrations switch already comply (pinned). Unknown keys are kept only from parsing (utils/unknownFields.ts) and written before the known fields, so a known field always wins; entries a map record can't read are kept as stored, and an unreadable reflection counts as "already reflected" and never earns XP. Details in PACKS_REPORTS_SPEC.md section 17.
  - Exceptions: the onboarding record keeps its privacy whitelist (only the known fields are written, so answers and Q10 never reach storage). The radar's starting outline is replace-only: a retake replaces it and carries none of its keys, since they would describe the outline being replaced.
  - Rules for newer builds: never change an existing field's type or widen its allowed values; add a new field instead. These records stay at `version: 1`; a breaking change uses a new key, as F-1 does (an older build reads another version as corrupt, and some paths replace a corrupt record).
  - Odd states: a record written by a newer update and re-saved by an older one. Tests: tests/decided-rules.test.ts (P-8: rollback tests per record, negative tests and a source scan), and the golden-snapshot upgrade tests (Phase 3).
- F-1, reflections split per year; a failed read never lowers XP or level (built in Phase 1b, 2026-11-13): reflections live in one item per year, `reflections:v2:<uid>:<yyyy>`, with the marker `reflections:migrated:v2:<uid>`; the old `reflections:v1:<uid>` is read and merged in (also after a rollback wrote to it) but never written or deleted. A read that fails rejects, never "no reflections": the screens keep the last numbers they showed (Home keeps its placeholder when none were shown, the rule for every stats failure), and a limit check with no known level uses the level from ticks alone and, if that refuses, says "Couldn't check your level just now. Try again in a moment." without naming a level. Details in PACKS_REPORTS_SPEC.md sections 12 and 17.
  - Later step: delete `reflections:v1:<uid>` after the next store build. Accepted: about 20 reflections a day with text (only by un-ticking and re-ticking) passes Android's per-item read limit within a year.
  - Odd states: a kill mid-migration, an older build saving to v1, v1 unreadable after migration (skipped), a corrupt year, a wrong-clock year. Tests: tests/reflections-years.test.ts, tests/decided-rules.test.ts (F-1).
- R-1 (built in Phase 1b, 2026-11-13): the area map's entries of habits known to be deleted (SQLite deleted = 1) are pruned at the next area write; a habit not on this phone, or a failed read of the deleted ids, prunes nothing. And storage that couldn't be read is never written over: areas, packs (a typed result every caller handles; the picker, pack edit and pack delete show their existing alerts), the onboarding record (a retake creates its habits and skips the record write), celebrated, the insight cache, the sync cursors and the startup trace. Exempt, with reasons, in PACKS_REPORTS_SPEC.md section 17.
  - Sync cursors: a failed read ends that cycle before any network call and leaves initialPullDone as it was; never an automatic reset. After 3 such cycles in a row Settings shows, muted, under its title: "Backup paused: this phone couldn't read its backup progress. It will keep trying." (approved 2026-11-13); it goes after the next cursor read that works. Never on Home, never a dialog, never on the startup path (the same file test as S-1).
  - Odd states: unreadable storage in each store, a corrupt value (still replaced), a large account with many deleted habits, a habit not on this phone. Tests: tests/r1-storage.test.ts, tests/sync-status-line.test.ts, tests/cursor-store.test.ts.
  - Celebrated keys that can't be read (added with S-4): every celebration of that tick or reflection is held and nothing is marked, so a level or milestone celebrated in an earlier run can't show again; ordinary toasts still show. Accepted cost: one reached meanwhile is never celebrated.
- S-4 (built in Phase 1b, 2026-11-13): "Add the rest" and a Settings retake create nothing until this uid's first pull has finished on this phone (sync/syncEngine.js firstPullFor: the engine's status for this uid, else the stored sync state; 'unknown' when that can't be read). Until then a tap shows "Your habits are still being restored. Stay online and try again in a moment." (approved 2026-11-13; "Add the rest" in the pack's notice, the plan row under the row; no dimmed look). Picking packs and the habit form are not blocked. Details in PACKS_REPORTS_SPEC.md section 17.
  - Known gap: a phone that never goes online after a sign-in stays blocked for these two actions. Phase F (guest mode): a guest has no server copy, so firstPullFor must treat a guest as 'done'.
  - Tests: tests/s4-first-pull.test.ts (S4-1 to S4-5, the R-1 interplay, corrupt state, parser-version bump, "Re-sync everything", fixtures pulledFromB and skippedThenRetake).
- P-2 (built in Phase 1b, 2026-11-13): renaming or deleting the only habit in a built-in pack that carries a template's name puts that template in the pack's `dropped`, so "Add the rest" doesn't create it again; renaming back takes it out. Only the habit form renames or deletes; there is no undo-delete. An unreadable active-habits list or pack record changes nothing, silently. No user-facing copy. Details in PACKS_REPORTS_SPEC.md section 17.
  - Known gaps: renames before P-2 aren't repaired (fixture renamedPackHabit pins it); renames and deletes pulled from another phone don't change this phone's pack record. Planned fix (redesign phase): store each habit's template id on the habit itself, synced, replacing name matching; not a pack-record field.
  - Tests: tests/p2-rename-delete.test.ts, tests/odd-state-fixtures.test.ts (renamedPackHabit).

## Orphan Auth accounts (parts (a) and (b) built 2026-11-14)
An orphan is a Firebase Auth account with no users/{uid} profile (admin Overview counted 72 profiles, Stats 73 Auth accounts). Causes: the old sign-up rollback's account delete failing after a refused profile write (swallowed), a kill or a hang between account creation and the profile write (the profile write had no timeout, and the in-memory Firestore cache loses a queued write when the app dies), accounts created outside the app (the public Auth endpoint, the console), a failed run of scripts/seed-test-accounts.mjs, older builds, and a profile deleted by hand. An orphan works (sync, the insight function), but admins can't see or disable it, and Settings > Your name can't save.
- (a) Prevention, complete forward instead of rolling back: sign-up saves the details on the phone first (`profile:pending:v1:<uid>` = {version: 1, age, firstName, lastName}, utils/profilePending.ts), right after the Auth account exists; then one profile write with a 10 s timeout (services/profileCompletion.ts). If it isn't confirmed, sign-up still succeeds and the completer (services/profileCompletionCore.ts) finishes it on sign-in, launch, foreground and after a sync cycle while something is pending, never on the startup path: it reads the server first (a late write is never written twice), writes, and drops the record once the profile is there. The account is never deleted; the old rollback delete is gone. The record is never re-saved, so P-8 doesn't apply; a corrupt or unreadable one is never acted on (R-1). Remaining gap: a kill in the moment between account creation and the pending write; recovery catches it.
- (b) Recovery: services/useDisabledCheck.ts already reads users/{uid} from the server (no extra read). Only when that read says the profile is missing (offline or any error is "unknown" and never counts) and nothing on this phone can complete it, "Finish setting up your account" (app/profile-setup.tsx) opens and blocks (no back, no swipe). Approved copy (2026-11-14): title "Finish setting up your account"; body "We couldn't save your details when you signed up. Add them to keep using HabitQuest."; button "Save and continue"; failure "Couldn't save your details. Check your internet connection and try again." Age and names use the sign-up validators. Under 18: the existing "You must be at least 18 to use HabitQuest.", nothing is written, and the user is signed out; the account is never deleted on this path. Accounts created outside the app rely on this screen.
- Admins (added 2026-11-14): an admin account made in the console has no profile by design. Only when the profile is server-confirmed missing, the same check reads admins/{uid} from the server (no extra read for normal users). If it exists, recovery never opens and any pending record is left alone; if that read fails, it counts as unknown and nothing is done. A normal user with no profile still gets the screen (services/profileCompletionCore.ts settleProfile, utils/profilePending.ts profileAction).
- Phase F (guest mode, not built): a guest has no profile by design and must be exempt from this check.
- (c) Planned, later step (approved, not built): the nightly stats count orphans (Auth accounts with no profile id; load.js already reads every profile id, so no extra reads) as an additive `orphans` field on stats/{day}; the admin Stats screen shows "Accounts without a profile", and Overview's "Total users" becomes "Profiles". A Cloud Functions change: deployed separately, outside the OTA freeze.
- (d) Planned, later step (approved, not built): functions/scripts/find-orphans.mjs, read-only (uid, creation and last sign-in times, provider, habit and completion counts; no emails). Only empty, never-used accounts are deleted, by hand in the Firebase console.
- Tests: tests/orphan-profile.test.ts; the sign-up pins in tests/auth-session.test.ts, tests/onboarding-0b.test.ts, tests/onboarding-gate.test.ts and tests/profile-name.test.ts.

### The rules (Set 1; utils/awards.ts, every one with boundary fixtures in tests/awards.test.ts)
Terms. *Today* is the phone's local date (getLocalDateString). Every rule looks only at dates up to and including today. A habit's created date is clamped to today (S-2). An *active* habit is not deleted. A habit is *scheduled* on a date when it is active, created on or before that date, and daily or due on that weekday, by its CURRENT schedule (the known limitation of all stats). A *tick* is a completion row marked done; ticks of deleted habits count wherever a rule counts ticks (as XP and the overall streak do), so deleting a habit never takes a tick-based award away. A *perfect day* has at least one scheduled habit and every scheduled habit ticked (countPerfectDays, unchanged). A *missed day* is a date before today with at least one scheduled habit and none of the scheduled habits ticked. Today is still open: it can earn, never break.
- **Streaks** `streak_3` `streak_7` `streak_14` `streak_30` `streak_60` `streak_100` `streak_200` `streak_365`: the longest overall streak (computeStreaks, unchanged) is at least N.
- **Perfect days** `perfect_1` `perfect_7` `perfect_30` `perfect_100`: at least N perfect days.
- **Perfect runs** `perfect_run_3` `perfect_run_7`: at least N perfect days in a row, where a day with nothing scheduled is skipped (neither counts nor breaks), a day before today with something scheduled that is not perfect breaks the run, and today counts once it is perfect. So a Monday-to-Friday user can earn a perfect week across a weekend.
- **Volume** `done_10` `done_50` `done_100` `done_250` `done_500` `done_1000`: at least N ticks in total (each a habit on a date).
- **Steady week** `steady_week`: some 7 consecutive dates, the first on or after the earliest created date of any habit and the last on or before today, in which the scheduled habit-days add up to at least 7 and at least 80% of them are ticked. Each habit counts once per date it is scheduled; ticks on unscheduled dates and on deleted habits don't count here.
- **Steady month** `steady_month`: the same over 30 consecutive dates (the same first and last date limits), at least 30 scheduled habit-days, at least 80% ticked. Today may be the last date of a window; its habits not yet ticked count as not ticked.
- **Never twice** `never_twice`: some 30 consecutive dates (the same first and last date limits) with at least 20 dates that have something scheduled, and no two consecutive dates that are both missed days.
- **Weekend done** `weekend_done`: a Saturday and the Sunday after it are both perfect days.
- **Back again** `comeback`: a tick on a date at least 4 days after the previous date with a tick (three or more dates without a tick between them). It needs an earlier tick: a first-ever tick is not a comeback.
- **Habit mastery** `habit_streak_7` `habit_streak_30` `habit_streak_66`: some active habit's longest streak on its own scheduled dates is at least N (a scheduled date before today without its tick resets it; unscheduled dates are skipped; today counts once ticked). Deleting that habit takes the award away; the other groups never lose one that way.
- **Five going** `habits_5`: at least 5 active habits right now.
- **Areas** `areas_3` `areas_6`: the active habits' icons cover at least 3 (or all 6) areas through the icon-to-area table (utils/radar/areas.ts ICON_AREA); a General icon, or an icon this build doesn't know, counts toward no area. The on-phone area choices and packs are not read.
- **Time** `days_7` `days_30` `days_100` `days_365`: at least one tick ever, and at least N days from the earliest created date of any habit (deleted ones included) to today.
Tiers: the streaks bronze, silver, gold, emerald, ruby, blaze, and blaze with a second flame (200) and with a laurel (365); perfect days bronze to emerald; perfect runs silver and gold; volume bronze to blaze; steady week silver, steady month gold, never twice emerald, weekend done bronze; back again bronze; mastery bronze, gold, ruby; five going bronze; areas silver and gold; time bronze, silver, gold, blaze.
